# lansync — 局域网文件夹同步（C）

服务端常驻；客户端启动后在局域网里自动找到它、连上去接受管理，
把本地目录与服务端目录比对一次并同步，然后退出。

|  |  |
|---|---|
| **判定** | 只看**大小 + 修改时间**，一致时零读取（30 GB 目录首次比对几秒） |
| **传输** | **TLS 1.3**（X25519 / Ed25519 / ChaCha20-Poly1305），**没有明文开关** |
| **写入** | 服务端默认**只读**；要写回得过**六位验证码** |
| **体积** | Android 发布版 **285 KB**（upx 后），单文件，不需要 root |
| **依赖** | 纯 C11 + POSIX；wolfSSL 静态链接，运行时只要系统自带的 `libc`/`libm`/`libz`/`libdl` |

## 快速开始

```bash
sh certs/gen.sh     # 1. 生成密钥对（仓库里不含私钥）
make                # 2. 构建 Linux 调试版 + Android 两版
```

```bash
# 3. 服务端（常驻）。默认：它是只读的权威源，客户端被改成本目录的副本
./build/lansync_d server -d /srv/share

# 4. 客户端（另一台机器）；目录省略则为当前目录
./build/lansync_d client -d ~/share
```

### 产物

| 产物 | 说明 |
|---|---|
| `build/lansync_d` | Linux 调试版（本机跑测试用） |
| `build/lansync-android-arm64` | Android 发布版：strip + upx，不含任何诊断输出 |
| `build/lansync-android-arm64-d` | Android 调试版：带 `-DLS_DEBUG`，不 strip 不 upx |

**排查问题要用带 `-d` 的调试版。** 发布版里 `ls_dbg` 展开成 `((void)0)`，
连参数字符串都不会进二进制 —— 发现请求、判定细节这类输出全都没有。

其它目标：`make test`（端到端测试，70 项）、`make test-hash`（校验 gxhash 与上游一致）、
`make android`（只出 Android 两版）、`make clean`。

想量自己机器上的哈希吞吐（判断哈希会不会拖慢同步）：

```bash
make hash-bench            # 在开发机上跑
make hash-bench-android    # 出 Android 版，按提示推到手机上跑
```

纯内存操作，不写盘。轮数可用 `HASH_BENCH_ROUNDS=32` 调小。

### 部署到 Android

```bash
adb push build/lansync-android-arm64 /data/local/tmp/lansync
adb push certs/lansync-server.crt certs/lansync-server.key /data/local/tmp/
adb shell chmod 755 /data/local/tmp/lansync
adb shell /data/local/tmp/lansync server -d /sdcard/share
```

**服务端必须和证书、私钥在同一目录**（默认按可执行文件所在目录找，也可用
`--cert` / `--key` 指定）。少了私钥服务端直接起不来 —— 没有降级成明文的选项。

客户端**不需要任何文件**：服务端证书已经编进它的二进制里了。

### 关于密钥

`src/server_cert.h` 里的证书字节是客户端的**唯一**信任锚，所以：

- 换密钥就**必须两端都重编**
- `certs/lansync-server.crt` 可以公开；`certs/lansync-server.key` **别外传** ——
  谁拿到它，谁就能冒充你的服务端

## 命令与选项

### 命令

```bash
lansync server -d /srv/share                # 服务端（常驻）
lansync client -d ~/share                   # 客户端：自动发现并同步一次
lansync client -d ~/share -s 192.168.1.10   # 不等发现，直连指定 IP
lansync client update                       # 把自己更新成服务端上的版本（同架构）
lansync discover                            # 只搜索局域网里的服务端
lansync entropy /srv/share                  # 看目录里有多少数据值得压缩
```

`lansync <命令> -h` 看常规选项，`--help-debug` 看含调试项的完整帮助。

### 选项

| 选项 | 作用 |
|---|---|
| `--prefer server\|client\|newer` | 冲突时谁赢，默认 `server` |
| `--keep-extra` | 不删除客户端多出的文件 |
| `--allow-upload` | 允许客户端写回服务端，**跳过验证码**（等于完全信任客户端） |
| `--merge` | 双向合并 = `--prefer newer --keep-extra --allow-upload` |
| `--verify hash\|meta` | 按内容哈希比对，或只比大小 + 时间（默认 `meta`） |
| `--compress auto\|on\|off` | 传输压缩，默认 `auto` |
| `--client-subdir DIR` | 让客户端落在它自己目录下的 `DIR/` 里 |
| `--dist PATH` | `client update` 下发的程序（默认本进程自身） |
| `--code NNNNNN` | 固定六位验证码，只给测试/自动化用 |
| `--cert` / `--key` | 服务端证书与私钥的路径 |
| `--config PATH` | 剖析/调参配置文件（默认 `lansync-server.json`） |

`--prefer client` / `--prefer newer` 要真正让服务端被写，还得通过验证码
（或显式 `--allow-upload`）—— 策略不会偷偷放行写入。

`--client-subdir` 由服务端在握手时下发，客户端日志会打印
`服务端指定落盘位置：xxx/`。客户端只接受不含 `..` 的相对路径。

## 同步是怎么判的

### 默认：服务端只读

**服务端目录永远不会被客户端修改或新增**，客户端上比服务端新的同名文件也覆盖不了它。
服务端启动时会明确打印：

```
策略：服务端优先 + 客户端多出的文件会被删除；服务端只读，客户端无法修改或新增本目录的任何文件
```

要允许写回，得过六位验证码（见「安全模型」），或显式 `--allow-upload`。

### 判定规则：只看大小 + 修改时间

判定完全基于元数据（都取纳秒精度）：

1. **扫描只 stat**，记录路径 / 大小 / mtime —— 几万个文件也就几秒
2. **大小和 mtime 都相同** → 判相同，**不读文件内容**
3. 否则按 `--prefer` 决定覆盖方向

| 情况 | 默认动作 |
|---|---|
| 只有服务端有 | 推送到客户端 |
| 只有客户端有 | 删除客户端的副本（`--keep-extra` 则忽略） |
| 两边都有，大小与 mtime 都相同 | **判为相同，绝不重传** |
| 大小或 mtime 有一个不同 | 服务端版本覆盖客户端 |

实测（100 MB / 200 个 500 KB 文件，两端完全一致）：

| 方案 | 耗时 | 实际读取 |
|---|---|---|
| 全量 MD5 | ~1900 ms | 200 MB |
| 采样块核对 | ~150 ms | 13 MB |
| **大小 + mtime（现在）** | **7 ms** | **0** |

30 GB 目录首次比对也就几秒，**全程不读文件内容**。

### 会漏判什么（重要）

**已知漏判：文件被原地修改、大小不变、且 mtime 也没变。**

最容易撞上的是「同一个文件在同一毫秒内被重写」：实测 f2fs 上
`echo A > a; echo B > b` 两条命令写出的文件 mtime **纳秒级完全相同**。
程序化快速改写（脚本、构建产物）会遇到，人工编辑不会。

为什么仍然选它 —— 曾经实现过「随机采样若干 4 KB 块算哈希」来核对内容，
实测被否掉：1 MiB 文件只覆盖 8/256 个块，逐块改 1 个字节的**漏判率是 14/16**。
mtime 方案只在上面那种极端情况漏，而且一个字节都不用读。

| 方案 | 漏判条件 | 读取量 |
|---|---|---|
| 全量 MD5 | 无（密码学强度） | 100% 文件内容 |
| 采样块 | 改动落在未采样的 97% 区域（**实测 87.5% 漏判**） | ~32 KB/文件 |
| **大小 + mtime**（默认） | 同一毫秒内原地重写（罕见） | **0** |
| **大小 + gxhash**（`--verify hash`） | 64 位哈希碰撞（可忽略） | 100%（但哈希 28.7 GB/s，瓶颈是磁盘） |

要消掉最后一类漏判就开 `--verify hash`：多付一次全盘读取（24 GB 约 24 秒）。
要密码学强度（防**恶意构造**碰撞）仍应上 `rsync -c` 或全量 SHA ——
gxhash 是非密码学哈希，抗碰撞但不抗构造。

### mtime 不可靠时怎么办

不同文件系统对 mtime 的支持差别很大，处理分两层：

**1. 精度差异 → 容差比较。** f2fs 记到纳秒，Android 的 FUSE（`/storage`）只剩秒。
严格按纳秒比会永远判「不同」，于是每次同步都全量重传。现在差值在 **2 秒内**视为同一时刻。

**2. 根本设不上 → 改用内容哈希。** 客户端启动时会在同步目录里放一个探针文件，
把 mtime 设成 2020-01-01 再读回来核对：

```
警告：本机文件系统无法保留文件修改时间（/sdcard/share）
```

结果通过 `HELLO2` 报给服务端，服务端据此改用**内容哈希**比对：

```
[phone] 该设备保不住 mtime，改用内容哈希比对（要读一遍它的文件）
[phone] 内容哈希：128 个相同 / 2 个不同
```

只有本机 CPU 连 AES 指令都没有时，才退回只比大小：

```
[phone] 该设备保不住 mtime，本机又没 AES：只能退化为「只比大小」
[phone] 其中 2 个文件只是大小相同就判为相同（客户端保不住 mtime，没能比对时间）
```

两条路径下**首次同步都正常**（客户端没有的文件照传）。

## 安全模型

### 传输加密（TLS 1.3）

**所有 TCP 通道一律加密，没有明文开关。** 唯一例外是 UDP 发现（见本节末尾）。

- 密钥交换 X25519，认证 Ed25519，对称 ChaCha20-Poly1305
- 客户端**内置**服务端证书（`src/server_cert.h`），那是它唯一接受的信任锚
- 服务端持有对应私钥（`certs/lansync-server.key`，本地文件）

### 谁证明谁

| 方向 | 手段 | 挡住什么 |
|---|---|---|
| 客户端认服务端 | 内置证书做信任锚 | 局域网里冒充服务端（ARP 欺骗、假热点、同名服务端） |
| 服务端认客户端 | 六位验证码（只在写回时） | 陌生设备偷偷往服务端写东西 |

只读同步**不需要**验证码：任何设备连上来都能把文件拉走，但改不了服务端一个字。
只有要往服务端写，才需要「能同时看到两块屏幕的人」批准一次。

### 六位验证码怎么走

```
        服务端生成六位码 ──TLS──> 客户端显示在自己屏幕上
                                          │
        服务端终端提示输入 <───────────────┘  操作者照着客户端屏幕敲
```

所以凭据其实是「你在场」这件事：局域网里别的设备看得到服务端，
却看不到那台客户端的屏幕。

- 批准才执行写回；不批准 / 超时 120 秒 / stdin 读不到（后台跑、`</dev/null`）
  一律按只读处理
- `--allow-upload` 跳过验证码；`--code NNNNNN` 用固定码（测试/自动化）

实现上有一处不显然的地方：**计划必须先用 `can_upload=1` 算一遍**。
因为默认只读策略下 `server_wins()` 恒选服务端，pull 项永远是 0，验证码根本没机会问。
算出来看到确实要写、又没获准时，再用 `can_upload=0` 重算一遍，计划就退回只读语义了。

### 没有「忘了加密」这种写法

`ls_send_all()` / `ls_recv_all()` 是所有 TCP 收发的**唯一出口**，而它们只对已登记
TLS 会话的 fd 工作 —— 没登记就直接返回错误。所以哪里漏了握手，那里会立刻失败，
而不是悄悄退回明文。

### 边界：UDP 发现仍是明文

发现请求/应答发生在握手之前，是广播，本来就没法加密。它暴露的只有服务端名称、
端口和目录路径。真要连这个也藏起来，就只能用 `-s` 指定 IP、跳过发现。

## 功能

### 传输压缩

**bundle 级压缩**：一整批文件走同一个 deflate 流，多个小文件共享压缩上下文，
比逐个压划算。靠每个条目结束时的 `Z_SYNC_FLUSH` 保证边界 ——
「一个条目的数据解压后恰好是它的 `size` 字节」，接收端不必猜切分点。

```bash
lansync server -d /srv/share                   # 默认 auto
lansync server -d /srv/share --compress on     # 一律压
lansync server -d /srv/share --no-compress     # 不压
```

`auto` 模式采样最多 32 个文件的前 8 KiB 算平均熵，**低于 6.5 才压**：

```
DBG  压缩：7000000 -> 2015293 字节（29%）
DBG  [phone] 本批推送 3 个文件，6.7 MiB（已压缩）
```

jpg/mp4/zip/apk 的熵在 7.5 以上，压了白费 CPU，auto 会自动跳过。
客户端不需要配置 —— 按 `BUNDLE_BEGIN` 里的标志解压。

### 内容哈希（`--verify hash`）

```bash
lansync server -d /srv/share --verify hash
```

两种情况下启用：

| 触发 | 说明 |
|---|---|
| `--verify hash` | 服务端点名要 |
| 客户端保不住 mtime | 时间戳失去可比性，自动改用哈希 |

用 **gxhash**（`third_party/libgxhash_arm64.a`）：Rust 写的，从它编出的 `staticlib`
（24 MB，把整个 std 打了进去）里**抽出唯一含 `gxhash32/64` 的那个目标文件**再打包，
5696 字节。链接器本来就只拉这一个目标文件，实测最终二进制只涨 **2476 字节**。

实测吞吐 **28.7 GB/s** —— 比手机闪存顺序读（~1 GB/s）快一个数量级。
所以哈希白送，代价全在**为了算它得把每个文件读一遍**：24 GB 目录约 24 秒。

两端都不无脑全读：

- **客户端**：要报给服务端，所以扫描后统一算一遍（带进度条）
- **服务端**：**惰性**算 —— 只有「大小相同、进到内容比对那一步」的文件才被读；
  大小不同的文件在第一步就被挡掉了

没开 `--verify hash` 且 mtime 正常的场合，行为与以前完全一致：**零读取**。

**硬门槛：CPU 要有 AES 指令。** gxhash 直接用 ARMv8-A 的 `aese`/`aesmc`，
**没有软件回退**，跑在不支持的 CPU 上就是一条 `SIGILL`。所以启动时先问内核
`getauxval(AT_HWCAP) & HWCAP_AES`，拿不到就让整个哈希功能缺席、退回只比大小。
`LANSYNC_NO_HASH=1` 可以强制模拟这条路径（测试用它覆盖「没有 AES」的分支）。

各实现的实测吞吐（`make hash-bench`，纯内存，单机）：

| 实现 | 吞吐 | 说明 |
|---|---|---|
| gxhash | **59–68 GiB/s** | 需要 AES 指令；比读盘还快一个数量级，白送 |
| SHA-256（armasm，有 SHA2 扩展） | 1.2–1.6 GiB/s | 和闪存顺序读（~1.5 GiB/s）同量级 |
| SHA3-256（纯 C） | ~0.44 GiB/s | wolfSSL 软件实现里最快的 |
| SHA-512 / BLAKE2s（纯 C） | ~0.33–0.36 GiB/s | |
| SHA-256（纯 C） | ~0.15–0.18 GiB/s | |

**判断"够不够用"要拿网络当尺子，不是拿闪存读。** 真正的瓶颈是链路：
手机热点实测 **37 MB/s**，5G/WiFi 撑死也就 100 MB/s 上下。对照上表，连最慢的
纯 C SHA-256 都比它快 1.5–5 倍，SHA3-256 快 5–13 倍 —— 所以**软件哈希完全够用**。
算 24 GB 用 SHA3-256 约 55 秒，而这批数据传输要 11 分钟，占比不到 10%。

拿闪存读当尺子会得出相反的（错误的）结论 —— 那只在"纯本地全盘比对"这种
不涉及网络的场景才成立，而那种场景本来就可以用零读取的 mtime 判定绕开。

所以真要给没有 AES 的设备兜底，**直接用 wolfSSL 现成的 SHA3-256 就行**：
零额外代码、够快。**不要**去移植 gxhash —— 它的内核用软件写出来只有
328 MiB/s，比 SHA3-256 还慢。

**分块规则**（gxhash 只有一次性接口 `gxhash64(buf, len, seed)`，没有流式 API）：

```
每块固定 LS_CHUNK（256 KiB），最后一块是余数
blk = gxhash64(块内容, len, SEED_BLOCK ^ 块起始偏移)
acc = gxhash64(&blk, 8, acc)
```

偏移进 seed，所以**交换两个块会被检出**（纯异或累积则不会）。
`read()` 必须攒满一整块再算 —— 短读会改变分块边界，让两端算出不同的值。

### 熵值分析（`entropy`）

```bash
lansync entropy /srv/share             # 汇总
lansync entropy /srv/share -v          # 逐文件列出熵值
lansync entropy /srv/share -n 131072   # 调整采样字节数
```

对每个文件采样开头若干字节（默认 64 KiB）算香农熵：

```
熵值分布
  易压缩 (<6.0)       22 个   978.4 KiB   33.4%
  中等   (6.0~7.5)      0 个         0 B    0.0%
  已压缩 (>7.5)        1 个     1.9 MiB   66.6%

结论：约 978.4 KiB（33%）的数据熵值不高，压缩可能有明显收益。
```

熵 < 6 基本是文本/日志/JSON/源码，压缩收益大；> 7.5 基本是 jpg/mp4/zip/apk
或加密数据，再压等于白费 CPU。

`entropy` 是**诊断工具**，跟同步时的 `--compress auto` 各自独立采样，互不依赖。

### 版本一致性

不做向前兼容 —— 两端必须是**同一次构建**，否则协议字段对不上，会出错得莫名其妙。

这也是握手要分两步的原因：`HELLO`/`HELLO_ACK` 只放版本信息、格式永不改动，
所以任何版本差异都能被识别出来、进而沿着这条连接取回新程序；能力协商放在
`HELLO2`，那边可以随时加字段。细节见「内部：架构与协议」里的时序图。

编译时刻由 Makefile 注入（`-DLS_BUILD_TS`），启动时打印：

```
lansync 1.0 (built 2025-10-02 03:47:53)
```

握手时两端交换这个时间戳，不一致时客户端会问：

```
本机与服务端不是同一次构建：
  服务端  2025-10-02 03:47:53  (build 1790913195)
  本机    2025-10-02 03:20:11  (build 1790911567)
是否从服务端更新本程序并退出？[y/N]
```

回答 `y` 就直接走更新通道（复用同一条连接取回程序本体并替换自己），
回答 `n` 或非交互环境则退出。`--ignore-version` 可以强行继续。

**更新通道始终保留**，只是不写兼容旧协议的代码。
`client update` 默认覆盖正在运行的本程序，也可以 `-o PATH` 存到别处；
下载完先 chmod 755，再 `rename` 原子替换。

### 传输健壮性

- 条目数据长度由 ENTRY 声明的 `size` 界定，**一个坏文件不会污染连接上后续的文件**
- 收发都有 300 秒超时，对端卡死不会让本端永久阻塞
- 失败会带上具体原因，例如
  `发送失败：a.chk —— 打开源文件失败: /path/a.chk (Permission denied)`
- 文件走 256 KiB 分片，落盘先写同目录临时文件再 `rename`，因此不会出现半个文件

### 性能剖析与自动调参

服务端每轮同步结束会写一份 `lansync-server.json`（`--config PATH` 可改）：

```json
{
  "role": "server",
  "total_ms": 22,
  "bytes_raw": 700000,
  "bytes_wire": 203283,
  "bottleneck": "transfer",
  "compress_level": 1,
  "phases": [
    {"name": "scan",     "ms": 0,  "pct": 0.0,  "detail": "3 个文件"},
    {"name": "transfer", "ms": 19, "pct": 86.4, "detail": "3 推送 / 0 拉取"}
  ]
}
```

日志里也会直接给结论，不用翻文件：

```
性能：耗时 22 ms，瓶颈是「transfer」占 86%；传输 683.6 KiB（线上 198.5 KiB）
```

**自动调参**：`compress_level` 会被读回来用在下一轮，并按实测调整：

| 实测 | 调整 |
|---|---|
| 吞吐 < 8 MB/s | 多半是压缩拖后腿 → 级别 −1 |
| 吞吐 > 25 MB/s 且压缩率 > 50% | 压得更狠省带宽 → 级别 +1 |

客户端**不写配置文件** —— 它默认几乎不发送数据，调参没有意义，结论只打在日志里。

## 内部：架构与协议

### 一切走流

文件内容不直接通向 socket，中间隔着一层流：

```c
LsSource  ── read()  ──┐                      ┌── write() ── LsSink
（文件、将来：压缩流）  ├── 传输层只认字节流 ──┤  （文件、将来：内存缓冲）
```

`LsSink` 是「先写同目录临时文件、finish 时 rename」的落盘汇，另有 `ls_sink_null()`
用于本地写不了时把数据读完丢掉。要加压缩、小文件先攒内存、打包，只需换一个流实现，
**协议和传输层一行都不用动**。

### bundle：一批文件 = 一个字节流

```
MSG_BUNDLE_BEGIN {count}
  MSG_BUNDLE_ENTRY {rel, size, mtime, mode}
  MSG_BUNDLE_DATA  {bytes}          ← 长度由前一个 ENTRY 的 size 界定
  MSG_BUNDLE_ENTRY {rel2, ...}
  MSG_BUNDLE_DATA  {bytes}
MSG_BUNDLE_END
MSG_BUNDLE_ACK {ok, msg, done, failed}
```

一次往返传几百个文件（实测 3000 个小文件 325 ms）。

**关键性质：协议天然对齐。** 数据段长度由 `size` 界定，发送端某个文件打不开或读一半
出错，就少发它的数据，接收端发现长度不符就丢弃它 —— **后面的文件照常**。
不再需要「失败时必须补发结束标记」那套脆弱逻辑。

### 协议

TCP 单连接、服务端驱动；消息 = `type(1B) + 长度(4B 大端) + 载荷`，
载荷内是 `u32/u64/i64` 大端整数和`长度前缀字符串`，
因此**文件名可以含空格、中文、任意字节**。

```
客户端                                     服务端
  │ HELLO {协议版本, build_ts} ───────────────────────────>│ 第一步：只放版本信息
  │<── HELLO_ACK {协议版本, build_ts, 编译时刻} ───────────│ 更新通道走的就是这一步
  │                                         │ 不一致 -> WANT_SELF 取回新程序
  │ HELLO2 {名字, 目录, mtime_ok, has_aes} ───────────────>│ 第二步：能力协商
  │<── HELLO2_ACK {服务端名, 目录, 策略, 落盘子目录,        │ 以后加字段加这里
  │                hash_algo}                              │
  │ LIST_BEGIN + LIST_CHUNK* + LIST_END    │ 路径/大小/mtime（+内容哈希，按需）
  │──────────────────────────────────────>│
  │                                         │ 判定：先比内容哈希（服务端那侧
  │                                         │ 惰性算），再退回大小+mtime
  │<──────── PLAN {推送/拉取文件数与字节数} │ 让进度条贯穿整场而不是每块重来
  │<──── UPLOAD_CODE {六位码} ─────────────│ 仅在需要客户端写回、且未获准时
  │<──── BUNDLE_BEGIN/ENTRY/DATA*/END ─────│ 推送（一批一次往返）
  │──── BUNDLE_ACK ───────────────────────>│
  │<──── PULL_WANT {路径...}               │ 仅在获准写回时才有
  │──── BUNDLE_BEGIN/ENTRY/DATA*/END ─────>│
  │<──────────────────────── BUNDLE_ACK    │
  │<──── DELETE {路径}                     │ 镜像模式
  │<──── SYNC_DONE {统计} + BYE            │
```

**握手为什么分两步**：`HELLO`/`HELLO_ACK` 是**更新通道的入口** —— 两端构建不一致时，
客户端要沿着这同一条连接把新程序取回来。所以这两条消息只放版本信息、**格式永不改动**；
一旦往里加字段，老客户端会因解析失败被拒连，从此再也更新不了自己。
其余一切「能力」都在 `HELLO2`/`HELLO2_ACK` 里，那边加字段随便加，
最坏只是能力协商失败，不会连累更新通道。

`hash_algo` 是服务端定死的本轮内容哈希算法（`0` 不算 / `1` gxhash / `2` SHA3-256），
客户端照它算 —— 两种算法对同一文件算出的值毫无关系，混用就没法比。
清单里每个条目的哈希为 `0` 表示没算过，服务端会退回按元数据判它。

`client update` 走同一条连接：客户端发 `WANT_SELF`，服务端用同一套 bundle
把它自己的可执行文件发过来。这条路径**不需要**第二步握手（不涉及目录与能力协商）。

### 局域网发现

UDP 广播：服务端应答 `LANDSYNC_DISCOVER`，并每 3 秒广播一次 `LANDSYNC_ANNOUNCE`。
广播会发往每个接口的子网广播地址（多网卡不会漏），枚举接口用 `SIOCGIFCONF`，
兼容 Android API 21。

## 故障排查

### 客户端找不到服务端

客户端不带 `-s` 时会发 UDP 广播找服务端。这条路出问题时，两端都有东西可看。
**服务端要用调试版**（`lansync-android-arm64-d`）跑，发布版里没有这些输出。

**客户端**（`discover` 或 `client` 的日志）会打印广播实际发往的地址，带接口名：

```
广播已发往 3 个地址：255.255.255.255,192.168.0.255(wlan0),192.168.44.255(bt-pan)
```

这是第一道判断：

- **里面没有服务端所在网段** → 发送端的问题。手机接口多
  （wlan0/ap0/bt-pan/ccmni\*），广播发错网段就等于没发。确认 Wi-Fi/热点连着、
  且那个接口有 IPv4 地址。
- **地址对了还是收不到** → 去看服务端。

**服务端**（调试版）收到发现请求会记一条：

```
[06:56:16.219] DBG 收到来自 192.168.0.42 的发现请求，已从接口 40 回复（TCP 端口 9527）
```

- **有这条** → 请求到了、也回了，问题在回程
- **没这条** → 广播根本没到服务端：不在同一网段、路由器开了 AP 隔离，
  或者服务端压根没在跑。**`discover` 必须在服务端开着的时候跑**，
  否则必然「没有发现任何服务端」

（这条按源 IP 各自限频 5 秒，一个客户端有多个接口时不会刷屏。）

实在查不出来就直接 `-s 服务端IP` —— 发现只是省得记 IP，TCP 那条路完全独立。

### 开着 VPN / 梯子时自动发现会失效（已修）

实际踩到过的坑，症状很迷惑人：

- `client -s 服务端IP` **完全正常**（TCP 能连、能同步，一路跑完）
- 自动发现却**永远失败**，客户端一条应答都收不到
- 服务端日志显示收到请求、也回复了，`sendto` 返回成功、毫无错误

根因是**无连接的 UDP 每次收发都要重查路由表**，而开着梯子时到同一个 Wi-Fi 里
其他设备的流量会被 VPN 的路由规则劫持：

```
$ ip route get 192.168.0.13
192.168.0.13 dev tun0 table 1076 src 10.255.0.1     ← 本该走 wlan0
```

于是回复包从 VPN 出去，永远到不了客户端。TCP 不受影响，因为它**走的是已建立
连接绑定的那个 socket，不重查路由** —— 这正好解释了上面「TCP 行、UDP 不行」的怪现象。

现在收到请求时会把入接口记下来（`IP_PKTINFO`），回复指定从**同一个接口**出去，
不再重新查路由；广播发送也按接口指定。开着梯子也能自动发现。

同一个服务端会从每个接口各回一份，客户端会**逐个尝试连接**，不只看第一个：
手机上有 tun0/VPN 这类接口时，先到达的那个地址不一定连得上。

### 服务端起不来

- 缺证书/私钥：先跑 `sh certs/gen.sh`，并确认 `certs/lansync-server.crt` 与
  `.key` 跟二进制在同一目录（或用 `--cert` / `--key` 指定）
- 证书与私钥不配套：两个文件必须是同一次 `gen.sh` 生成的

### Android 上「能列出文件、读不出内容」

服务端启动时会自检：**从目录里真读一个文件**。Android 上以 root 走
`/storage/emulated/0`（FUSE 挂载）时常见这种症状 —— 扫描一切正常、
传输时每个文件都失败。自检会直接点出来并给出两条出路。

## 设计取舍与实测

这些是跑出来的数字，不是估的。优先级取舍都基于它们。

### 瓶颈是网络，不是磁盘或 CPU

手机热点实测 3.0 GiB / 84 s ≈ **37 MB/s**，客户端剖析里 `recv` 占 99%。
对照：闪存顺序读 ~1.5 GB/s，gxhash 28.7 GB/s。

→ 「省 CPU / 省磁盘」的改动（并行压缩、异步落盘、更快的哈希）在同步音乐这类场景
**没有收益**；值得优化的只有链路本身和传输量。

### 压缩对已压缩内容完全无效

同步音乐时压缩率 100%，auto 直接判定不压、连启动都不启动。
只有文本/代码这类低熵内容才有收益（实测 7 MB → 2 MB，29%）。

### 为什么不换 QUIC

局域网 RTT < 2 ms、丢包接近 0，QUIC 的收益场景（高丢包、高 RTT、连接迁移、
多路复用）在这里全都不成立。它反而引入用户态协议栈、TLS1.3+AEAD 的 CPU 开销
和一堆 Android 链接依赖。

实测本机 loopback TCP 单流 **2151 MB/s**，而实际瓶颈是 Wi-Fi 链路（30–80 MB/s）
和磁盘小文件随机写（5–50 MB/s），协议层完全不是瓶颈。真要提高小文件吞吐，
该做的是批量打包而不是换传输协议。

### 已知边界

- **认证只到「服务端身份 + 写回授权」**：只读同步对局域网内任何设备开放，
  这是刻意的（拉走文件不是威胁模型的一部分）
- 判定依赖 mtime，见「会漏判什么」
- 多客户端同时同步时服务端串行处理，避免互相踩写
- 不做符号链接，跨文件系统时 `rename` 会失败（同目录内不会）
- gxhash 需要 CPU 有 AES 指令，没有就退回只比大小
- UDP 发现是明文，见「安全模型」

## 开发

### 测试

`make test` 共 70 项，覆盖：

- 大小与 mtime 都一致 → 判相同、不重传、零读取
- 大小不同、大小相同但修改时间不同
- 两端各自独有、多级子目录、1 MiB 多分片大文件、空文件、含空格与中文的文件名
- **默认服务端只读**：客户端更新的同名文件覆盖不了服务端，同步前后服务端目录
  `md5sum` 逐字节不变
- `--keep-extra` 时客户端多出的文件被忽略，服务端仍不被写
- 镜像删除、`newer` 策略下客户端赢、路径穿越被拒绝
- 8 个 200 KB 文件元数据一致时全程零内容读取
- 1 MiB 同大小、时间不同的文件能判出差异并同步
- **mtime 不可用 → 改用内容哈希**：客户端告警、服务端切到哈希、同大小不同内容
  被认出并正确同步，且第二次同步收敛（不重传）
- **没有 AES 时退回只比大小**（`LANSYNC_NO_HASH=1` 模拟）：退化到已知代价，不崩
- **`--verify hash`**：大小与 mtime 都对得上的文件，内容不同也能认出；内容一致时
  不误报差异
- `client update` 取回的二进制与服务端逐字节一致
- **压缩传输**：低熵内容被压、高熵文件完整、解压后逐字节一致、`--no-compress` 真的不压
- 传输后**修改时间原样保留**（发秒值会把客户端文件打成 1970）
- **单个文件读不了时不拖垮其余文件**：其余照常同步，失败原因指向具体文件与 errno
- **写回要过六位验证码**：码正确才写得进去；码不对、或服务端读不到输入（超时 /
  `</dev/null`）一律按只读处理，服务端文件一个字节都不变

`make test-hash` 另拿上游 `is_stable` 的原始测试向量（22 个长度 × 4 个种子 +
`gxhash32`）校验 C 接口，见 `test/hash_vectors.c`。这条特别重要 ——
它钉死了「哈希跨平台稳定」这个前提，换个 `.a` 就能立刻发现。

### `third_party/wolfssl/`

静态库和头文件已经放在仓库里，`make` 直接用，**不需要你另外装 wolfSSL**：

| 路径 | 内容 |
|---|---|
| `third_party/wolfssl/android/libwolfssl.a` | Android（bionic）静态库 |
| `third_party/wolfssl/linux/libwolfssl.a` | Linux（glibc）静态库 |
| `third_party/wolfssl/include/` | 公共头文件（只放了实际用到的那些） |
| `third_party/wolfssl/<平台>/wolfssl/options.h` | 各平台自己的编译配置 |

两个平台**不能共用同一个 `.a`**（libc 不通用），`options.h` 也随平台差一项
（`WC_RNG_AUTOFORK`），所以头路径按平台分。

库的配置是 `--enable-tls13 --enable-ed25519 --enable-curve25519 --enable-chacha
--enable-poly1305 --enable-armasm --enable-asm`，并关掉了 RSA / DH / DSA / TLS1.2 /
MD5 / RC4 / DES3；编译带 `-ffunction-sections -fdata-sections`，链接时靠
`--gc-sections` 按**函数**而不是按 `.o` 裁剪（静态链接默认以 `.o` 为单位，
一个 `.o` 里几十个函数只要引到一个就全拉进来；实测这一步省约 25%）。

> **`--enable-armasm` 不能省（踩过）**：它的帮助里写着 `default: disabled`，
> 不显式打开就得到一份**纯 C** 的库 —— 功能都对，但 SHA-256 只有 ~190 MiB/s，
> 打开后是 **1.2–1.6 GiB/s**（差 6 倍以上），TLS 的 ChaCha20/Ed25519/X25519
> 也一并失去硬件加速。代价是发布版 +42 KB。
>
> wolfSSL 的 ARM 汇编自带**三级运行时回退**，不需要你替它操心兼容性：
> `Sha256_SetTransform()` 读 HWCAP 后选择 `Transform_Sha256_Len_crypto_aarch64`
> （用 `sha256h`）→ `_neon_aarch64` → 纯 C `Transform_Sha256_Len`。
> 反汇编可以验证三份实现都在二进制里，而 crypto 指令**只**出现在专用的
> `L_sha256_len_crypto_begin` 段中，公共路径里一条都没有 —— 所以在没有
> SHA2/AES 扩展的 CPU 上会安静地走回退，而不是 `SIGILL`。

> **重建库时的坑（踩过）**：wolfSSL 的 `configure` 只在 `ENABLED_ED25519` 还是 `no`
> 的那条路径上加 `-DHAVE_ED25519_KEY_IMPORT`。显式传 `--enable-ed25519` 反而会跳过它，
> 于是服务端签名时报 `ASN parsing error, invalid input`（-140），而证书加载、TLS 握手
> 前面几步全都正常，很难查。重建库时务必手动补上：
>
> ```
> CPPFLAGS="-DHAVE_ED25519_KEY_IMPORT"
> ```

> **RPK 走不通（对照结论）**：RPK（RFC 7250 裸公钥）在「Ed25519 + 本版本 wolfSSL」
> 下是死的 —— 私钥不带公钥时 `Ed25519CheckPubKey()` 会去调 `wc_CertGetPubKey()`，
> 而那是个硬编码的 X.509 解析器，喂裸 SPKI 必然报同一个 -140。
> 所以这里用**自签 X.509 证书**而非 RPK。
